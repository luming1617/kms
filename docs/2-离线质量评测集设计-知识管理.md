# 一、 最值得关注的公开基准

目前已经形成了几类成熟的公开基准；
但截至 2026 年 10 月，没有找到一个被广泛采用、能够完整覆盖文档导入、解析、切分、向量索引、检索、更新和删除全生命周期的统一基准。

现有基准主要解决三个问题：
1. RAG 应用质量：给定问题、知识内容及相关证据，判断系统能否检索并正确回答。
2. 检索与 Embedding 能力：判断相关文档能否被检索到，适合比较 Embedding、检索器和重排器。
3. 文档解析质量：判断 PDF、表格、公式及复杂版面能否被准确转换成可用内容。

这些基准可以组合使用，但不能直接等同于完整的企业知识库管理测试。

## 1. RAGBench

优先推荐

端到端 RAG

适用场景： 评估知识库问答质量、比较检索与生成方案。

公开数据集约有 9.5 万条样本，包含 12 个子数据集，涉及技术手册、金融、医疗、法律等多个领域。其中的 EManual 和 TechQA 等子集对技术文档问答具有参考价值。

Datasets at Hugging Face

## 2. CRAG（Comprehensive RAG Benchmark）

复杂问答与动态知识

适用场景： 多领域事实问答、信息时效性、知识图谱和外部 API 检索。

CRAG 提供问题、答案、检索内容，以及模拟知识图谱和 API 的环境；测试问题覆盖不同领域、问题类型和知识时效性。官方基准还定义了对回答进行 Perfect、Acceptable、Missing、Incorrect 等类别评判的方案。

+1

## 3. BEIR

检索器基准

适用场景： 比较稠密检索、稀疏检索及混合检索方案。

BEIR 汇集不同领域的信息检索任务，覆盖事实核查、问答、生物医学、新闻、论点检索和重复问题检索等场景，支持 NDCG@K、Recall@K 等检索指标。

+1

[官方 GitHub](https://github.com/beir-cellar/beir?utm_source=chatgpt.com)

## 4. MTEB

Embedding 基准

适用场景： 选择 Embedding 模型，评估语义检索与相似度表现。

MTEB 提供覆盖检索、语义相似度、分类、聚类等任务的评测集合，当前官方文档列出了超过 1,000 个任务，覆盖多语言和多模态。具体选择应以其中的 Retrieval 任务为主。

## 5. CRUD-RAG

中文 RAG 基准

适用场景： 中文知识密集型任务、生成、知识问答及文本修正。

这项研究将 RAG 应用划分为 Create、Read、Update、Delete 四类。需要特别注意，它定义的 Update 是修正已有文本中的错误或不一致，而 Delete 是将较长文本压缩成摘要。

## 6. OmniDocBench

文档解析基准

适用场景： 检查知识库上游的 PDF 解析、版面识别、表格提取和阅读顺序。

OmniDocBench 提供 1,651 个 PDF 页面，带有文本块、表格、公式以及阅读顺序等标注，可用于比较解析器的输出与标准结果。


它非常适合验证知识库导入管道中的文档解析组件，但不直接评价解析后进入向量索引的全部流程。

[官方 GitHub](https://github.com/opendatalab/OmniDocBench?utm_source=chatgpt.com)

另外，KILT 适合有明确证据来源要求的知识密集型任务，RAGTruth 适合研究 RAG 回答中的幻觉与不受证据支持的内容。这两个也可以作为专项评测数据集补充。

参考入口：[KILT](https://ai.meta.com/tools/kilt/?utm_source=chatgpt.com) · [RAGTruth](https://github.com/ParticleMedia/RAGTruth?utm_source=chatgpt.com)

# 二、公开基准怎么选：不要试图用一套数据覆盖所有阶段

结合你希望评测的知识管理全流程，我建议分成下面四层。

|评测层|优先使用的数据集|能解决的问题|
|---|---|---|
|文档解析|OmniDocBench；表格密集型文档可补充 PubTables-1M|文本、表格、阅读顺序与结构提取是否正确|
|Embedding 与检索|MTEB、BEIR|模型选型、检索 Recall、排序质量|
|RAG 端到端|RAGBench、CRAG；中文专项可考虑 RGB、CRUD-RAG|检索、回答正确性、噪声干扰、信息整合|
|知识更新、删除与索引一致性|自建业务测试集|更新是否生效、旧版本是否残留、删除是否彻底、权限是否正确|

PubTables-1M 是另一项值得考虑的表格提取基准，包含大量表格及其结构、单元格和位置标注；但它针对的是表格检测和结构识别，而不是完整的 RAG 系统。


这里最关键的结论是：

公开数据集帮助你验证通用能力，自有测试集帮助你验证业务知识的正确性，而生命周期测试用例帮助你验证知识库软件本身是否可靠。

例如，BEIR 可以帮助比较不同检索器，RAGBench 可以帮助检查问答质量，但只有专门设计的更新测试，才能验证一份已经更新的合同条款是否还会被旧向量错误召回。

## 1. 使用 Ragas 从自己的文档生成 RAG 测试集

这是我推荐的第一种实现方式。

Ragas 的测试集生成流程可以从输入文档构建知识图谱，通过 LLM 与 Embedding 模型扩展文档信息，再生成不同类型的问题。官方提供的生成策略包括单跳具体问题、多跳具体问题和多跳抽象问题等。



其基本流程是：
[[_resources/d97507abd82f8bd24f4c59b622803c77_MD5.jpg|Open: Pasted image 20261022192953.png]]
![[_resources/d97507abd82f8bd24f4c59b622803c77_MD5.jpg]]

先从文档原文生成问题，而不是先把问题交给 RAG 系统，再用 RAG 自己的回答作为标准答案。否则，错误可能从生成环节传播到测试集。

### 可以生成哪些类型的问题？

建议至少覆盖以下问题类型。

|类型|示例|主要验证目标|
|---|---|---|
|单跳事实|产品 A 的规格参数是多少？|基础检索和事实提取|
|多跳推理|根据规格和限制条件，产品 A 是否满足某场景要求？|多个证据片段能否共同支撑答案|
|表格查询|某型号的额定功率和工作温度分别是多少？|表格解析及字段关联|
|版本相关|当前生效的政策规定是什么？|版本筛选与时效性|
|不可回答问题|文档没有提供该型号的额定压力，应如何回答？|正确拒答，避免编造|
|证据冲突|两份文档提供不同参数，哪一个有效？|来源可信度、时间及冲突处理|

其中，多跳问题和不可回答问题非常重要。单纯生成大量“根据文档回答是什么”的问题，很容易形成一个表面上分数很高、实际难以发现系统缺陷的测试集。

### Ragas 生成时要保存什么？

不要只保留问题和答案。建议同时保存证据来源：

``` json
{
  "case_id": "kb-spec-0001",
  "question_type": "multi_hop",
  "question": "产品 A 是否满足场景 B 的使用条件？",
  "reference_answer": "根据参数 X 和条件 Y，可以得出……",
  "source_documents": [
    {
      "document_id": "spec-A",
      "document_version": "v2",
      "page": 12
    },
    {
      "document_id": "scenario-B",
      "document_version": "v1",
      "page": 4
    }
  ],
  "evidence": [
    "与答案直接相关的原文片段"
  ],
  "answerable": true
}
```

这只是建议的内部数据格式，不是 Ragas 强制要求的 Schema。

建议使用 `document_id + version + page/section + evidence span` 作为主要证据标识，而不要把某个 Chunk ID 作为唯一的黄金依据。因为更换切分策略后，Chunk ID 可能发生变化，但原文证据仍然有效。

官方教程：[Ragas Testset Generation](https://docs.ragas.io/en/latest/getstarted/rag_testset_generation/?utm_source=chatgpt.com)

## 2. 使用 DeepEval 的 Synthesizer 生成测试集

DeepEval 同样能够从文档生成 `Golden` 样本，再将其转换为测试用例。

官方提供的接口包括 `generate_goldens_from_docs()`、`generate_goldens_from_contexts()` 等。前者涉及文档上下文构建，后者则从已有上下文生成测试集。

![[_resources/184e93a95c5e442bb5ff58df78ef57ec_MD5.png]]

DeepEval - The LLM Evaluation Framework

+2

示意代码如下：

``` python
from deepeval.synthesizer import Synthesizer

synthesizer = Synthesizer()

goldens = synthesizer.generate_goldens_from_docs(
    document_paths=[
        "docs/product_spec.pdf",
        "docs/operation_manual.docx",
        "docs/current_policy.md",
    ],
)

print(f"生成了 {len(goldens)} 个候选测试样本")
```

注意：这段示例演示的是 DeepEval 当前文档中的生成模式。正式运行时，应根据安装版本确认具体参数、异步选项、模型适配器及输出类型。

Ragas 和 DeepEval 不需要同时承担全部测试集生成任务。 我更建议先选一个作为主要生成器：已有 Ragas 流程就继续用 Ragas；如果希望直接把生成的 Golden 接入 DeepEval 测试工程，则可以使用 DeepEval Synthesizer。

生成完成后，两个框架的结果都应转换为同一个内部 JSONL 格式，方便后续统一执行和管理。

### 生成数据如何保证质量？

自动生成的数据一定要经过审核，尤其是高风险的业务知识。

建议采用以下流程：

1. 检查问题可回答性：标准答案是否真的能从指定的原始文档中推导出来。
    
2. 检查证据充分性：多跳问题是否标注了全部必要的来源文档。
    
3. 检查答案正确性：由业务人员复核关键实体、数值、日期、版本及否定关系。
    
4. 删除重复问题：不能仅依据文本完全相同判断重复，还要处理语义高度相近的问题。
    
5. 补充难例：缺失文档、相互冲突、过期内容、同名实体及不完整表格。
    
6. 固定测试版本：审核通过的数据才进入正式黄金测试集；未审核数据只能作为候选样本。
    

对一般文档问答，可以使用模型辅助审核；对于资金、法律、权限和安全相关的知识，应将确定性规则与领域专家复核作为主要标准。

# 四、文档导入、切分、更新和删除的测试集，怎样单独生成？

这部分不适合只靠 Ragas 或 DeepEval 的问答生成器。

原因很简单：即使某个测试集生成了 1,000 道正确的 QA，它也不一定包含“同一个文档更新两次，然后删除，再用旧关键词搜索”的测试场景。

生命周期测试应采用可控的测试文档 + 预设操作序列 + 明确的预期状态。

## 1. 文档解析测试集

从真实文档中选出有代表性的文件，并为每个文件准备人工核验后的标准解析结果。

建议覆盖 PDF、Word、Excel、HTML、Markdown，以及有扫描页、表格、标题嵌套、脚注和复杂阅读顺序的文档。

公开基准如 OmniDocBench 和 PubTables-1M 可以提供解析及表格结构方面的通用测试样本；但你的自有文档仍然需要建立黄金解析结果。

![[_resources/0190d796e82f0eb3db3633114059d207_MD5.png]]

GitHub

+1

测试集至少要保存：

- 原始文件及文件哈希。
    
- 标准正文、标题层级和关键表格。
    
- 标准元数据。
    
- 允许忽略的噪声，例如页眉页脚。
    
- 必须完整保留的关键事实。
    
- 对应解析器及版本。
    

## 2. 切分测试集

不必为每种切分方案规定一模一样的 Chunk 边界。否则，测试实际上是在强制要求某个固定的切分结果，而不是验证切分质量。

更好的办法是保留源文本位置、段落和证据片段，然后检查：

- 有效内容覆盖率。
    
- 关键事实是否被拆散。
    
- 标题与正文的关联是否保留。
    
- 表格的表头与单元格是否仍然可关联。
    
- 每个 Chunk 能否追溯到原始文档。
    
- 不同切分配置下，最终检索与回答质量是否改善。
    

如果某类文档确实有明确的语义边界要求，例如每个表格的标题、表头及主体必须保持关联，那么可以对该类文档建立专门的结构断言。

## 3. 更新和删除测试集

建议编写一个小型测试文档生成器，能为每个测试用例创建确定的 V1、V2 文档，以及唯一标识的测试事实。

例如：

```
用例：kb-update-delete-001

导入 V1：
产品 ZX-901 的测试费率为 0.15%。
测试标识：CANARY-V1-901

更新 V2：
产品 ZX-901 的测试费率为 0.12%。
测试标识：CANARY-V2-901

更新完成后断言：
1. 当前查询能够找到 V2 的事实。
2. 当前答案不得把 V1 作为有效规则。
3. 已失效的 V1 不能通过正常当前状态查询再次命中。

删除文档后断言：
1. V2 不再通过普通知识库检索返回。
2. 搜索 CANARY-V1-901、CANARY-V2-901 都不能召回已删除内容。
3. 在约定 SLA 后，索引与元数据满足删除策略。
4. 其他租户无法查看该文档的内容。
```

`CANARY` 字符串是专门生成的测试标识，方便在更新和删除测试中追踪某一份内容是否仍然存在。

这里要区分两种不同的正确性：正常查询不再返回已删除事实，是功能性验证；底层存储与索引不再保留应清理的数据，则是数据治理验证。两者需要分别设计断言。

## 4. 怎么自动生成这些生命周期用例？

可以使用 Python 按模板生成，而不必引入新的 LLM 评测框架。

每一个用例可以由四部分构成：

``` json
{
  "case_id": "kb-lifecycle-001",
  "initial_documents": [
    {
      "document_id": "doc-001",
      "version": 1,
      "content": "产品 ZX-901 的费率为 0.15%。"
    }
  ],
  "operations": [
    {
      "type": "UPDATE",
      "document_id": "doc-001",
      "version": 2,
      "content": "产品 ZX-901 的费率为 0.12%。"
    },
    {
      "type": "DELETE",
      "document_id": "doc-001"
    }
  ],
  "assertions": [
    {
      "stage": "after_update",
      "type": "CURRENT_FACT_EQUALS",
      "expected": "0.12%"
    },
    {
      "stage": "after_delete",
      "type": "CONTENT_NOT_RETRIEVABLE",
      "expected": true
    }
  ]
}
```

在执行时，Runner 根据 `operations` 调用真实知识库 API，并在每一个状态转换节点执行对应断言。

建议额外增加失败、重试、重复请求、超时和并发更新场景。例如，先提交 V2 更新，再模拟旧索引任务延迟完成，检查迟到的 V1 任务是否会覆盖新版本；这类问题通过纯问答基准通常发现不了。

# 五、如何建立一套有实际价值的黄金测试集？

我建议不要一开始就追求几千条测试样本，而应先建立一个规模不大、但覆盖清晰的基线。

下面是一个可作为第一阶段目标的配置，不是行业统一标准。

|数据集|建议首期规模|作用|
|---|---|---|
|RAG 黄金 QA|100–300 条|评估真实文档上的检索、证据和回答质量|
|文档解析黄金集|按文档类型分层抽取|验证正文、表格、标题和元数据保留|
|生命周期测试|为新增、更新、删除、重试及权限分别建立场景|验证知识库状态正确性|
|公共基准|选取与场景相关的测试子集|形成外部对照，减少对自建数据的依赖|
|生产失败回归集|持续积累|反映真实业务的长尾问题|

RAG 黄金 QA 建议覆盖单跳、多跳、表格、数字、版本、不可回答问题和权限场景，而不是平均分配到所有容易生成的题型。

另外，建议划分三个逻辑集合：

- 开发集：允许反复调试 Prompt、切分和检索参数。
    
- 锁定测试集：不直接用于调参，主要用于发布前回归。
    
- 线上回流集：来源于生产异常或真实用户反馈，审核后再加入下一版本测试集。
    

同一批问题反复用于参数调优，容易造成对测试集过拟合。因而真正用于发布决策的测试集，需要尽量避免参与日常开发调参。

# 六、最终建议

第一层：公开基准。 用 RAGBench 做端到端 RAG 的通用质量基线，BEIR 或 MTEB 评估检索器与 Embedding，OmniDocBench 检查文档解析能力。必要时再补充 CRAG、RGB 或 RAGTruth 等专项基准。
第二层：业务黄金数据集。 从真实知识文档出发，用 Ragas 或 DeepEval 生成候选问题和答案，再经过人工复核，保留来源文档、有效版本与证据标注。它是你持续对比系统质量的主力测试集。
第三层：生命周期自动化测试。 使用确定性的文档夹具和操作序列，检验导入、切分、索引、更新、删除、幂等及权限。它是完整知识管理能力的必要补充，不能由 RAG 的问答准确率代替。
第四层：持续评测。 将结果写入 Langfuse，统一保存测试版本、指标、失败案例及延迟成本，再将经过复核的线上问题转为新的回归测试。

这样，公开基准负责“与业界方法对照”，自有黄金集负责“是否适用于你的知识”，生命周期测试负责“知识库状态变化是否正确”。三者结合，才构成完整的知识管理测试体系。
